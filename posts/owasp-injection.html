01

OWASP Top 10 (2025) 소개

OWASP는 Open Worldwide Application Security Project의 약자로, 웹 애플리케이션과 소프트웨어의 보안을 개선하기 위해 활동하는 비영리 재단이자 오픈 커뮤니티이다.

웹 애플리케이션은 인터넷 브라우저를 통해 이용하는 프로그램을 말한다. 쇼핑몰이나 인터넷 뱅킹 등이 대표적인 예시이다.

OWASP는 개발자와 보안 담당자가 취약점을 이해하고 예방할 수 있도록 다양한 보안 자료와 가이드를 제공한다. OWASP Top 10은 웹 애플리케이션에서 중요하게 다뤄야 할 보안 위험 10가지를 정리한 목록이다.

보안 취약점(Vulnerability)이란 프로그램이나 시스템에 존재하는 보안상의 약점을 뜻한다.
순위취약점간단한 설명
A01접근 제어 취약점권한 없는 사용자가 다른 사람의 정보나 기능에 접근
A02보안 설정 오류잘못된 서버·시스템 설정으로 보안 문제 발생
A03소프트웨어 공급망 실패외부 라이브러리나 개발·배포 과정에서 보안 문제 발생
A04암호화 실패민감한 정보를 적절하게 암호화하거나 보호하지 못함
A05인젝션악의적인 입력이 명령어나 쿼리로 실행됨
A06안전하지 않은 설계설계 단계에서 필요한 보안 통제가 부족함
A07인증 실패로그인이나 사용자 신원 확인 과정의 취약점
A08소프트웨어·데이터 무결성 실패코드나 데이터가 변조되는 것을 적절히 방지하지 못함
A09보안 로깅 및 경고 실패공격 흔적을 기록하거나 관리자에게 알리지 못함
A10예외 상황 처리 실패오류나 예상하지 못한 상황을 안전하게 처리하지 못함
02

A05 인젝션을 이해하기 위한 기초 개념

클라이언트와 서버

웹사이트에 접속할 때는 크게 클라이언트와 서버가 서로 정보를 주고받는다.

클라이언트

서비스를 이용하고 정보를 요청하는 쪽이다. 예를 들어 웹 브라우저가 있다.

서버

클라이언트의 요청을 받아 처리하고 결과를 보내주는 컴퓨터 또는 프로그램이다.

클라이언트요청 →서버← 응답

데이터베이스

여러 정보를 체계적으로 저장하고 관리하는 시스템이다. 아래는 학생 정보를 저장한 테이블의 예시이다.

학번이름학과
2026001김철수컴퓨터공학과
2026002이영희정보보안학과
2026003박민서소프트웨어학과
  • 행(Row): 학생 한 명에 대한 정보
  • 열(Column): 학번, 이름, 학과처럼 정보의 종류

SQL이란?

SQL은 관계형 데이터베이스에서 데이터를 조회하거나 추가, 수정, 삭제할 때 사용하는 언어이다.

명령어역할
SELECT데이터 조회
INSERT데이터 추가
UPDATE데이터 수정
DELETE데이터 삭제
SELECT * FROM students WHERE name = '김철수';
  • SELECT: 데이터를 조회한다.
  • *: 모든 열을 선택한다.
  • FROM students: students 테이블에서
  • WHERE name = '김철수': 이름이 김철수인 데이터만 찾는다.
즉, students 테이블에서 이름이 김철수인 학생의 정보를 조회하라는 뜻이다.

쿼리란?

데이터베이스에 정보를 요청하는 명령이나 질의를 의미한다. 사용자가 검색창에 이름을 입력하면 서버는 해당 이름을 찾기 위한 SQL 쿼리를 만들어 데이터베이스에 전달할 수 있다.

인젝션 취약점은 이러한 쿼리를 안전하지 않은 방식으로 만드는 과정에서 발생할 수 있다.

입력값이란?

사용자가 프로그램에 전달하는 데이터이다. 로그인 화면의 아이디와 비밀번호, 검색어, 회원가입할 때 입력하는 이름 등이 대표적이다.

사용자가 입력한 값은 항상 안전하다고 보장할 수 없다. 따라서 프로그램은 입력값을 신뢰할 수 없는 데이터로 취급하고 적절하게 처리해야 한다.
03

인젝션 취약점의 정의와 발생 원인

인젝션은 프로그램이 외부에서 전달받은 데이터를 명령어와 안전하게 구분하지 못할 때 발생할 수 있다.

인젝션이 발생하는 과정

  1. 사용자 입력
    검색창 또는 로그인 입력창에 데이터 입력
  2. 서버에서 입력값 처리
    입력값을 기존 명령어와 안전하지 않게 결합
  3. 명령어의 의미가 변경됨
    입력 데이터 일부가 실행할 명령으로 해석됨
  4. 의도하지 않은 동작 발생
    정보 노출, 데이터 변경, 명령 실행 등

주요 발생 원인

첫 번째 · 입력값을 제대로 검증하지 않는 경우

프로그램이 입력값의 형식이나 범위를 확인하지 않으면 예상하지 못한 값이 전달될 수 있다. 다만 입력값 검증만으로 모든 인젝션을 예방할 수 있는 것은 아니다.

두 번째 · 입력값을 명령어에 직접 연결하는 경우

사용자가 입력한 문자열을 SQL 명령어에 그대로 이어 붙이면 입력값이 SQL 문법의 일부로 해석될 수 있다.

세 번째 · 안전하지 않은 실행 기능을 사용하는 경우

프로그램이 외부 입력값을 운영체제 명령어나 코드 실행 기능에 직접 전달하면 공격자가 프로그램의 동작을 변경할 가능성이 있다.

가장 중요한 원인은 신뢰할 수 없는 데이터와 실행할 명령을 분리하지 못하는 것이다.
04

인젝션 공격의 주요 유형

공격 대상과 명령어의 종류에 따라 여러 유형으로 나뉜다.

유형설명
SQL Injection데이터베이스에 전달되는 SQL 명령을 조작
NoSQL InjectionNoSQL 데이터베이스의 질의 조건 등을 조작
OS Command Injection서버 운영체제에서 실행되는 명령을 조작
LDAP Injection사용자·조직 정보 검색에 사용하는 LDAP 질의를 조작
Expression Language Injection프로그램의 표현식 평가 기능을 악용

OWASP Top 10:2025의 인젝션 범주에는 크로스 사이트 스크립팅(XSS)도 포함되어 있다. XSS는 웹페이지에서 공격자가 삽입한 스크립트가 실행되는 문제이다.

데이터베이스와 SQL의 기본 개념을 이해했다면 SQL 인젝션의 공격 원리도 비교적 쉽게 이해할 수 있다.

05

SQL 인젝션의 동작 원리

정상적인 SQL 조회

웹사이트에서 사용자가 자신의 아이디를 입력하면 서버가 다음과 같은 SQL을 실행한다고 가정해 보자.

SELECT * FROM users WHERE id = 'student1';

이 명령어는 users 테이블에서 아이디가 student1인 사용자의 정보를 조회한다는 뜻이다.

취약한 SQL 조회

그런데 서버가 사용자의 입력값을 SQL 문장에 그대로 붙여서 만든다면 문제가 발생할 수 있다. 예를 들어 공격자가 아래 문자열을 입력했다고 가정해 보자.

' OR '1'='1

서버가 이를 안전하지 않게 연결하면 SQL 명령어가 아래처럼 바뀔 수 있다.

SELECT * FROM users WHERE id = '' OR '1'='1';
  • OR는 두 조건 중 하나라도 참이면 전체 조건을 참으로 판단하는 연산자이다.
  • '1'='1'은 항상 참이므로 특정 사용자 한 명이 아니라 여러 사용자 정보를 조회할 수 있다.
단순히 아이디를 검색하기 위한 입력값이 데이터베이스 조회 조건 자체를 변경한 것이다. 이 예시가 실제 로그인 우회를 항상 의미하는 것은 아니다. 로그인 우회 여부는 서버의 인증 처리 방식에 따라 달라진다.

SQL 인젝션으로 발생할 수 있는 피해

SQL 인젝션이 성공하면 취약점의 위치와 데이터베이스 계정의 권한에 따라 개인정보 조회, 데이터 변경 및 삭제, 인증 우회 등이 발생할 수 있다.

모든 SQL 인젝션이 동일한 피해를 일으키는 것은 아니지만 데이터베이스의 중요한 정보를 직접 대상으로 한다는 점에서 위험성이 크다.

06

인젝션 취약점의 탐지 방법

인젝션을 예방하려면 프로그램에 취약점이 존재하는지 확인하는 과정도 필요하다.

소스 코드 분석

개발자가 작성한 코드를 살펴보면서 사용자 입력값이 SQL이나 운영체제 명령어에 직접 연결되는 부분이 있는지 확인하는 방법이다.

동적 보안 테스트

실제 실행 중인 프로그램에 다양한 테스트 입력을 전달해 비정상적인 응답이나 취약한 동작이 발생하는지 확인하는 방법이다.

퍼징(Fuzzing)

프로그램에 예상하지 못한 형식이나 다양한 입력값을 자동으로 전달하면서 오류나 보안 문제를 찾아내는 테스트 기법이다.

07

인젝션 공격의 예방 및 대응 방법

매개변수화된 쿼리 사용

SQL 인젝션을 예방하는 대표적인 방법은 매개변수화된 쿼리를 사용하는 것이다. SQL 명령어의 구조와 사용자가 입력한 값을 분리하여 입력값이 SQL 명령어의 일부로 해석되지 않도록 한다.

SELECT * FROM users WHERE id = ?;
  • ?는 나중에 데이터 값을 전달받을 자리이다.
  • 프로그램이 준비된 쿼리에 입력값을 안전하게 바인딩하면 해당 값은 SQL 명령어가 아니라 데이터로 처리된다.

입력값 검증

입력값이 예상한 형식과 범위에 맞는지 확인한다. 예를 들어 나이는 숫자만, 학번은 정해진 길이와 형식만 허용할 수 있다. 다만 매개변수화된 쿼리를 대신할 수는 없다.

최소 권한 원칙

프로그램이 데이터베이스에 접근할 때 꼭 필요한 권한만 부여한다. 학생 정보 조회 기능에 데이터베이스 전체 삭제 권한까지 줄 필요는 없다. 취약점이 악용되더라도 피해 범위를 줄일 수 있다.

지속적인 보안 점검

프로그램 개발 시뿐만 아니라 운영 중에도 정기적으로 취약점을 점검하고 보안 업데이트를 적용해야 한다. 새로운 기능이 추가되거나 입력값 처리 코드가 변경될 때도 확인해야 한다.

08

이번 주제에서 기억해야 하는 핵심

인젝션은 단순히 특수문자를 입력해서 발생하는 문제가 아니라, 프로그램이 외부 입력값을 데이터로 처리해야 하는데 이를 실행할 명령어의 일부로 해석하는 것이 핵심 문제이다.

따라서 인젝션을 예방하려면 입력값을 무조건 차단하는 것보다 명령어와 데이터를 안전하게 분리하는 구조를 만드는 것이 중요하다.

09

새롭게 알게 된 점 및 느낀 점

이번에 OWASP Top 10의 A05 인젝션을 공부하면서 인젝션이 단순히 악의적인 코드를 입력하는 공격이 아니라 프로그램이 사용자 입력값을 데이터와 명령어로 제대로 구분하지 못할 때 발생하는 보안 취약점이라는 것을 알게 되었다. 그리고 SQL 인젝션을 공부하면서 평소 아무 생각 없이 사용했던 로그인창이나 검색창에서도 보안 문제가 발생할 수 있다는 점이 기억에 남았다. 사용자가 입력한 값이 SQL 명령어에 그대로 연결되면 데이터베이스의 조회 조건이 변경될 수 있고 이로 인해 개인정보가 노출되거나 데이터가 변조될 수 있다는 사실을 알게 되었다.

인젝션을 예방하기 위해서는 단순히 특수문자를 차단하는 것만으로는 충분하지 않으며 매개변수화된 쿼리를 사용해 명령어와 데이터를 분리하는 것이 중요하다는 점을 배웠다. 이번 공부를 통해 웹사이트의 보안은 단순히 외부 공격을 막는 것뿐만 아니라 프로그램을 개발하는 과정에서 사용자의 입력값을 어떻게 처리하는지에 따라서도 달라질 수 있다는 것을 알게 되었다. 이제 SQL 인젝션뿐만 아니라 OS 명령어 인젝션과 같은 다른 유형의 공격도 공부하고 직접 실습 환경에서 취약한 코드와 안전한 코드의 차이를 비교해 보고 싶다.
